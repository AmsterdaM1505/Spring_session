# ADR 2 Раздельные JWT и проверка в сервисах

Статус: принято.

Booking выдаёт пользовательские JWT RS256 на 3600 секунд. Claim `sub` содержит неизменяемый числовой id пользователя, `roles` - USER либо ADMIN, issuer - `hotel-booking`, audience - `hotel-api`. Пароли хранятся только как BCrypt с cost 12. Регистрация всегда создаёт USER; выдача ADMIN возможна только через административный API или демонстрационное предзаполнение.

Gateway, Booking и Hotel независимо проверяют подпись, issuer, audience и временные ограничения. Методная безопасность защищает операции контроллеров. В Booking дополнительно проверяются активность текущего аккаунта и фактическая роль для административных операций. Чужая бронь возвращает 404, чтобы не раскрывать существование записи.

Внутренние операции Hotel используют отдельную RSA-пару, issuer `booking-internal`, audience `hotel-internal`, роль INTERNAL и время жизни 60 секунд. Роль INTERNAL не назначается пользователю. В Hotel для этих путей выделена первая SecurityFilterChain; она не принимает пользовательский JWT. Gateway запрещает пути release и confirm до маршрутизации.

У Gateway и Hotel нет закрытых ключей. Демонстрационные закрытые ключи лежат только в ресурсах Booking. Их открытое распространение допустимо исключительно для воспроизводимого локального стенда. При размещении меняются обе пары ключей и пароли; применяются HTTPS и ограничение прямого доступа к сервисам.

Ограничение JWT без общего хранилища отзыва: Hotel проверяет выданные роли до истечения токена. Изменение роли либо удаление аккаунта в Booking не отзывает уже выданный токен в Hotel немедленно. Сам Booking проверяет текущее состояние аккаунта. Максимальное окно устаревших прав Hotel - срок токена с допуском часов валидатора. Refresh token и централизованный отзыв не входят в ТЗ.
